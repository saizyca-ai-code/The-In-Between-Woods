# 狹間之森｜創作協作流程

- 文件狀態：初版
- 版本：v0.1
- 原則：流程支援創作，不預先限制創作

## 1. 三個系統的分工

| 系統 | 主要用途 | 不應被當成 |
|---|---|---|
| ChatGPT 專案 | 發想、討論、寫作、編輯、連續性檢查 | 唯一正式設定庫 |
| GitHub Projects | 管理素材卡片、工作進度、成熟度、正式性與關聯 | 正式正文的唯一保存處 |
| GitHub Repository | 保存正式文件、決策紀錄、協作方法與可追溯版本 | 必須一次定型的僵化資料庫 |

三者不會自動完全同步。完成一項重要工作時，明確說明哪些內容仍在對話中、哪些已記錄於 Project、哪些已寫入 Repository。

## 2. 一項素材的基本生命週期

### A. 捕捉靈感
先保存核心，不急著補齊全部欄位。可以是一句話、一個畫面、一段對白、一個矛盾或一種情緒。

### B. 整理與探索
協助釐清素材的可能意義、情感張力、角色需求、主題關聯與不同發展方向。新增想法標示為「提案」。

### C. 建立管理卡片
在 GitHub Projects 建立卡片，填入已知資訊。未知欄位可以留空，不要為了完整而虛構答案。

### D. 深入發展
當素材需要持續討論、比較方案或記錄問題時，可建立 GitHub Issue，並把 Issue URL 填入 Project 的「關聯文件」欄位。

### E. 確認決策
只有創作者明確同意後，才把構想標記為「已確認」。若重要決策會影響後續創作，將決策與理由寫入 Repository。

### F. 保存正式文件
依素材類型把正式內容寫入適當的 Markdown 文件，例如角色設定放在 `characters/`，世界規則放在 `world/`，章節正文放在 `stories/`。

### G. 組裝與重用
組裝章節時，從素材卡片與正式文件中找出人物選擇、因果、情緒轉折、節奏與主題呼應。素材被使用後仍可重用，不必自動封存。

### H. 修訂與追溯
修改已確認設定時，先辨識受影響的人物、章節、時間線和伏筆。不要只修改一處而忽略依賴它的其他文件。

## 3. 三種狀態不可混為一談

- **工作進度**：工作是否待處理、進行中、審閱中或完成。
- **正式性**：構想是否未確認、已確認、已否決或刻意留白。
- **成熟度**：素材是靈感碎片、初步構想、具體方案或可供採用。

例：某角色可以是「工作進度：審閱中、正式性：待確認、成熟度：具體方案」。這不是矛盾，而是三個欄位各自描述不同維度。

請以 GitHub Project 目前實際設定的選項為準；若本文件與現行欄位名稱不同，記錄差異並更新文件，不要假設兩邊已自動同步。

## 4. 「關聯文件」欄位怎麼用

建議放入一個最主要、可直接開啟的 URL：

- 討論中的素材：對應 GitHub Issue URL。
- 已有正式設定：對應 Repository 中的 Markdown 檔案 URL。
- 同時有多種關聯：主要 URL 放在欄位，其他關聯放進 Issue 或 Markdown 正文。

在 Markdown 正文中可以使用相對連結，例如：

```markdown
[角色設定](../characters/forest_keeper.md)
```

相對路徑必須依照實際檔案位置調整。不要填入尚未建立或未驗證的檔案連結。

## 5. 決策記錄

重要決策建議記錄：
- 決策內容
- 狀態：已確認／待確認／已否決／刻意留白
- 為什麼做出這個決定
- 曾考慮的替代方案（如有）
- 可能影響的角色、世界規則、章節或伏筆
- 關聯的 Project 卡片、Issue 與正式文件

並非每個小細節都需要決策紀錄。只有會影響連續性、後續創作或方法論的決策，才值得特別保存。

## 6. 協作方式

- 任務明確時直接執行；只有關鍵歧義會實質影響方向時才先提問。
- 發想階段保留多種可能，不過早定案。
- 編輯時具體指出問題位置、成因、影響與修正選項。
- 正文寫作遵循已確認設定，刻意留白不主動補完。
- 更新正式文件前，先查閱相關既有內容。
- 完成後只回報必要的成果、決策、連續性影響與保存狀態。

## 7. 以實際使用修訂流程

這份手冊是可演進的工作文件，不是不可更改的規章。若流程造成重複勞動、資訊遺失或分類困難，先記錄具體問題，再提出小幅修訂。不要因一次特殊情況就增加永久規則。
